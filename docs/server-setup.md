# Конфигурация виртуальной машины ubuntu-server

Практическая работа №5. Удалённый сервер и безопасный доступ: SSH, sudo, UFW, DNS.

## 1. Параметры виртуальной машины

Гипервизор: QEMU/KVM с управлением через libvirt (`qemu:///system`).

Имя виртуальной машины в libvirt: `ubuntu-server`.

Гостевая операционная система: Ubuntu Server 24.04.5 LTS, x86-64.

Имя узла внутри Ubuntu: `ms0ur-vm`.

Ресурсы: 2 vCPU, 2048 МиБ оперативной памяти, виртуальный диск `qcow2` объёмом 30 ГБ.

Диск расположен на гипервизоре по пути `/home/vm-storage/ubuntu-server.qcow2`. Внутри Ubuntu используется LVM: группа `ubuntu-vg`, логический том `ubuntu-lv`, файловая система ext4.

Текущий размер корневого раздела: **28G**.

## 2. Сетевые интерфейсы

Используется виртуальная сеть libvirt `default` с режимом NAT.

Гостевой интерфейс: `enp1s0`, модель virtio, адрес `192.168.122.50/24`.

Шлюз: `192.168.122.1`.

На гипервизоре сеть подключена через мост `virbr0`, имеющий адрес `192.168.122.1/24`.

На физическом сервере используется адрес `192.168.2.100`.

В отличие от типовой конфигурации VirtualBox, один интерфейс libvirt обеспечивает и исходящий доступ в интернет, и прямую связь с гипервизором. Для доступа с отдельного рабочего компьютера используется SSH-проброс.

Проверка внутри Ubuntu: `ip -brief address`, `ip route`.

Проверка на гипервизоре: `sudo virsh -c qemu:///system net-info default`.

## 3. Проброс портов

На физическом сервере создан systemd socket `ubuntu-server-ssh.socket`, прослушивающий `192.168.2.100:12222`.

Служба `ubuntu-server-ssh.service` использует `systemd-socket-proxyd` для перенаправления соединений на `192.168.122.50:2222`.

Пути конфигурации:

`/etc/systemd/system/ubuntu-server-ssh.socket`

`/etc/systemd/system/ubuntu-server-ssh.service`

Первоначально проброс направлял соединения на порт 22 гостевой ОС. После усиления защиты SSH порт назначения изменён на 2222. Внешний порт 12222 сохранён.

Для применения изменений systemd: `sudo systemctl daemon-reload`, затем `sudo systemctl restart ubuntu-server-ssh.service`.

На рабочем Linux-компьютере создан SSH-алиас `devops` с параметрами: HostName `192.168.2.100`, Port `12222`, User `devops`, IdentityFile `~/.ssh/devops_vm`, IdentitiesOnly `yes`.

Команда подключения: `ssh devops`.

## 4. Учётные записи

Первоначальная учётная запись: `ms0ur`.

Для администрирования создан пользователь `devops`, входящий в группы `sudo` и `users`.

Создание пользователя: `sudo adduser devops`.

Выдача административных прав: `sudo usermod -aG sudo devops`.

Для SSH создана отдельная ключевая пара Ed25519. Закрытый ключ хранится на рабочем компьютере в `~/.ssh/devops_vm`, открытый ключ добавлен в `/home/devops/.ssh/authorized_keys`.

Права доступа: каталог `.ssh` — 700, файл `authorized_keys` — 600.

После настройки защиты вход по SSH разрешён только пользователю `devops` и только с использованием открытого ключа.

## 5. Служба SSH

Основной конфигурационный файл: `/etc/ssh/sshd_config`.

Резервная копия: `/etc/ssh/sshd_config.backup`.

Дополнительный конфигурационный файл: `/etc/ssh/sshd_config.d/99-hardening.conf`.

Установлены следующие параметры:

| Параметр | Значение |
|---|---|
| Port | 2222 |
| PermitRootLogin | no |
| PasswordAuthentication | no |
| PubkeyAuthentication | yes |
| PermitEmptyPasswords | no |
| MaxAuthTries | 3 |
| LoginGraceTime | 30 |
| AllowUsers | devops |
| X11Forwarding | no |
| ClientAliveInterval | 300 |
| ClientAliveCountMax | 2 |

В `/etc/ssh/sshd_config.d/50-cloud-init.conf` закомментирована конфликтующая директива `PasswordAuthentication yes`.

Сокетная активация отключена через `sudo systemctl disable --now ssh.socket`. Служба включена через `sudo systemctl enable --now ssh.service`.

Проверка синтаксиса: `sudo sshd -t`.

Проверка действующих параметров: `sudo sshd -T`.

Проверка прослушиваемого порта: `sudo ss -tlnp | grep sshd`.

Перед изменением SSH необходимо оставить открытую действующую сессию, проверить новую конфигурацию и сохранить доступ через консоль гипервизора.

## 6. Межсетевой экран UFW

Межсетевой экран активен.

Политики по умолчанию: `deny incoming`, `allow outgoing`, `disabled routed`.

Разрешённые входящие подключения:

| Порт | Правило | Назначение |
|---|---|---|
| 2222/tcp | LIMIT | SSH, ограничение частоты подключений |
| 80/tcp | ALLOW | HTTP |
| 443/tcp | ALLOW | HTTPS |

Также действуют соответствующие правила IPv6.

Журналирование включено в режиме `medium`.

Настройка выполнялась командами:

`sudo ufw default deny incoming`

`sudo ufw default allow outgoing`

`sudo ufw allow 2222/tcp comment 'SSH'`

`sudo ufw allow 80/tcp comment 'HTTP'`

`sudo ufw allow 443/tcp comment 'HTTPS'`

`sudo ufw enable`

`sudo ufw limit 2222/tcp comment 'SSH rate-limited'`

`sudo ufw delete allow 2222/tcp`

`sudo ufw logging medium`

Правило LIMIT добавлялось до удаления первоначального разрешения SSH во избежание потери доступа.

Проверка правил: `sudo ufw status verbose`.

Блокировка проверена подключением к порту 8080. В `/var/log/ufw.log` зафиксировано событие `UFW BLOCK` с источником `192.168.122.1`, получателем `192.168.122.50`, протоколом TCP и портом назначения 8080.

## 7. Локальное доменное имя

На гипервизоре в `/etc/hosts` добавлено соответствие:

`192.168.122.50 devops.local`

В гостевой Ubuntu в `/etc/hosts` настроено:

`127.0.1.1 ms0ur-vm.devops.local ms0ur-vm`

Проверка `getent hosts devops.local` на гипервизоре возвращает `192.168.122.50`.

Проверка `hostname -f` внутри Ubuntu возвращает `ms0ur-vm.devops.local`.

Имя `devops.local` настроено на гипервизоре. Для использования с отдельного рабочего ПК потребуется обеспечить соответствующее разрешение имени и сетевой доступ.

## 8. Снимки состояния

Снимки создаются средствами libvirt на выключенной виртуальной машине.

| Имя снимка | Состояние |
|---|---|
| 01-clean-install | Исходная установка Ubuntu перед заданиями |
| 02-keys-configured | Создан пользователь devops и настроены SSH-ключи |
| 03-ssh-hardened | Настроена защита SSH |

Просмотр снимков: `sudo virsh -c qemu:///system snapshot-list ubuntu-server`.

Снимки используются для восстановления учебного стенда.

## 9. Восстановление конфигурации

Перед откатом следует сохранить необходимые изменения и убедиться, что выбран правильный снимок. Откат заменяет текущее состояние диска состоянием из снимка.

После возврата к `01-clean-install` требуется восстановить пользователя `devops`, его SSH-ключи, ограничения SSH, правила UFW и локальные имена.

Важно: на исходном снимке SSH использует порт 22, тогда как действующий прокси гипервизора направляет соединения на 2222. Поэтому после отката необходимо временно обеспечить доступ к гостевому порту 22 через гипервизор или консоль VM.

Восстановление включает создание пользователя, добавление публичного ключа в `authorized_keys`, восстановление `99-hardening.conf`, устранение конфликта с `50-cloud-init.conf`, переключение с `ssh.socket` на `ssh.service`, настройку UFW и файла `hosts`.

Далее проверяются `sudo sshd -T`, `sudo ufw status verbose`, подключение по ключу и успешный запуск `scripts/audit.sh` с кодом возврата 0.

**Примечание:** снимок `01-clean-install` содержит исходную конфигурацию Ubuntu. Он не включает изменения, выполненные в заданиях 4.1–4.4.
